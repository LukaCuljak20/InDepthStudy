# Event Manager: Express.js Micro-Prototype

Standalone micro-prototype for the individual in-depth study **Web Framework Exploration** (Track B) in
_Development of Web Applications (C1UT1B)_, Autumn 2026.

It implements CRUD for a single core entity, **`Event`**, taken from the Laboratory Assignment 2 event manager app
(C#, ASP.NET Core MVC, Entity Framework Core). The goal is not a complete application but a focused artifact that
shows how Express.js solves the same problem, so the two frameworks can be compared in the report.

> Research question: _What are the architectural advantages and disadvantages of Express.js, and how do its
> component model, state management and developer experience differ from ASP.NET Core MVC as applied in Lab 2?_

## Quick start

**Requirements:** [Node.js](https://nodejs.org) 18 or newer (LTS recommended) and npm.

```bash
git clone https://github.com/LukaCuljak20/InDepthStudy.git
cd event-manager-express
npm install
npm start
```

Open <http://localhost:3000>.

| Command       | What it does                                 |
| ------------- | -------------------------------------------- |
| `npm start`   | Start the server                             |
| `npm run dev` | Start with automatic restart on file changes |

Set a different port with the `PORT` environment variable (PowerShell: `$env:PORT=4000; npm start`).

On first start the app creates `data/events.json` with three sample events. Delete that file to reset the data.

## Features

- List, view, create, edit and delete events
- Filter the list by category and by "upcoming only" (query string)
- Server-side validation with [zod](https://zod.dev), including the cross-field rule "end must be after start"
- Form re-displayed with the user's input and per-field error messages when validation fails
- One-time flash messages after create, update and delete
- Custom middleware: request logger, flash messages, central error handling
- Custom 404 page (unknown URL or unknown event id) and a generic error page
- Server-rendered views with EJS (no client-side JavaScript framework)

## The `Event` entity

| Field         | Type     | Rule                                                  |
| ------------- | -------- | ----------------------------------------------------- |
| `id`          | number   | Generated by the repository                           |
| `title`       | string   | Required, max 100 characters                          |

```
├── middleware/
│   ├── requestLogger.js             # Logs method, URL, status, duration
│   ├── flash.js                     # One-time session messages
│   └── errorHandler.js              # 404 and 500 handling
├── views/
│   ├── partials/                    # header.ejs, footer.ejs
│   ├── events/                      # index.ejs, show.ejs, form.ejs
│   ├── 404.ejs
│   └── error.ejs
├── public/
│   └── style.css                    # Static files
└── data/

```

### Request flow

```
Request
  -> requestLogger        (logs when the response finishes)
  -> express.urlencoded   (parses form bodies into req.body)
  -> method-override      (turns ?_method=PUT/DELETE into real PUT/DELETE)
  -> express.static       (serves /style.css)
  -> express-session      (session cookie)
  -> flash                (moves the one-time message to res.locals)
  -> router               (routes/events.js -> eventController)
  -> 404 handler          (nothing matched)
  -> errorHandler         (renders 404 or error page)
```

## Routes

| Method | URL                | Handler    | Description                                        |
| ------ | ------------------ | ---------- | -------------------------------------------------- |
| GET    | `/`                | redirect   | Redirects to `/events`                             |
| GET    | `/events`          | `index`    | List, with `?category=` and `?upcoming=true`       |
| GET    | `/events/new`      | `newForm`  | Empty create form                                  |
| POST   | `/events`          | `create`   | Validate and create                                |
| GET    | `/events/:id`      | `show`     | Event details                                      |
| GET    | `/events/:id/edit` | `editForm` | Pre-filled edit form                               |
| PUT    | `/events/:id`      | `update`   | Validate and update (form posts to `?_method=PUT`) |
| DELETE | `/events/:id`      | `destroy`  | Delete (form posts to `?_method=DELETE`)           |

Browsers' HTML forms can only send GET and POST, which is why `method-override` is used for PUT and DELETE.

## Comparison with Lab 2 (ASP.NET Core MVC)

| Concern                | Lab 2: ASP.NET Core MVC                                      | This prototype: Express.js                          |
| ---------------------- | ------------------------------------------------------------ | --------------------------------------------------- |
| Application setup      | `Program.cs`                                                 | `app.js`                                            |
| Project structure      | Convention (`Controllers/`, `Views/`, `Models/`)             | Chosen by the developer                             |
| Routing                | Conventional or attribute routing                            | Explicit `router.get()` calls in `routes/events.js` |
| Controller             | `EventsController` with `IActionResult` methods              | Plain `(req, res, next)` functions                  |
| Model binding          | Automatic                                                    | Manual from `req.params`, `req.query`, `req.body`   |
| Validation             | Data Annotations, `ModelState.IsValid`, `IValidatableObject` | zod schema, `safeParse`, `.refine()`                |
| Views                  | Razor (`.cshtml`), strongly typed models                     | EJS (`.ejs`), untyped, partials instead of layouts  |
| Data access            | EF Core, `DbContext`, LINQ, migrations                       | Repository module over a JSON file                  |
| One-time messages      | `TempData`                                                   | Session-based flash middleware                      |
| Cross-cutting concerns | Middleware and filters                                       | Middleware only                                     |
| Error handling         | `UseExceptionHandler`, status code pages                     | Four-argument error middleware                      |
| Static files           | `wwwroot/`, `UseStaticFiles`                                 | `public/`, `express.static`                         |
| Type safety            | C#, compile-time                                             | JavaScript, runtime only                            |

Every source file also carries a comment naming its ASP.NET Core MVC counterpart.

## Design decisions and scope

- **JSON file instead of a database.** The assignment asks for a micro-artifact, not full database integration.
  Only `models/eventRepository.js` touches storage, so replacing it with Prisma or Sequelize would not change the
  controller. The file is not safe for concurrent writes, which is acceptable for a single-user demo.
- **Server-rendered EJS instead of a JSON API.** This is closer to the Razor/MVC model used in Lab 2, which keeps
  the comparison like for like.
- **Hand-written flash middleware** (about ten lines) instead of `connect-flash`, so the mechanism is visible and
  can be compared directly with `TempData`.
- **Plain JavaScript instead of TypeScript** to stay within the 4 to 8 hour scope. Type safety is discussed as a
  limitation rather than demonstrated.
- **Out of scope:** authentication and authorization, relationships (attendees, organizers), automated tests,
  CSRF protection, and deployment. The session secret in `app.js` is a development placeholder.

4. Create a valid event and point out the flash message and redirect.

## Troubleshooting

- **`'node' is not recognized` (Windows):** Node.js is not on your PATH. Install the LTS version, then fully close
  and reopen the terminal or editor so it picks up the new PATH. Check with `node -v`.
- **Port already in use:** start with another port, for example `$env:PORT=4000; npm start`.
- **Changes to `data/events.json` are ignored:** the file is re-read on every request, so edit it while the server
  is stopped or make sure the JSON stays valid.
